# Collab 2 — przejście krok po kroku

- Cel i minimum: R2.1–R2.4 w `1.brief.md`. Czytaj równolegle kontrakt; nie trzeba znać gotowego rozwiązania.
- Po każdym małym kroku: zapisz -> build -> uruchom -> sprawdź. Gdy gra jest uruchomiona, `start` nie wczyta nowych źródeł.

## Krok 1. Zabezpiecz działającą wersję

1. Uruchom swoją ukończoną grę, nie starter z GitHuba.
2. Sprawdź start, pojedynczy ruch, odmowę ściany i wygraną.
3. Zapisz aktualną wersję w Git; ustal faktyczną gałąź integracyjną.
4. W ZESPOL.md przypisz zadania według podziału na końcu pliku. Jeśli masz stare rozszerzenie z czterema flagami odwiedzin, zaznacz je do zastąpienia tablicą — nie utrzymuj dwóch źródeł prawdy.

## Krok 2. Zrozum indeks przed dotykaniem gry

1. Uruchom listing C2-A z `2.tech.md`
2. Zmień numer menu na ostatni poprawny, a następnie o jeden za duży
3. Powiedz partnerowi: co sprawdzasz przed odczytem i dlaczego?
4. Uruchom C2-C. Wyjaśnij, czemu tablica po wywołaniu wygląda inaczej.

## Krok 3. Wprowadź dane

1. Integrator dodaje przed pierwszym Start tablicę czterech nazw; nazwy odpowiadają waszej fabule.
2. Obok tworzy tablicę bool o czterech elementach. Nie dopisuje jeszcze nowych komend.
3. Build i commit wspólnej bazy; pozostali ją pobierają.
4. W tym czasie każdy w swoim projekcie prób tworzy tablicę trzech dowolnych nazw i wypisuje je z numerami. Nie dodawaj projektu prób do katalogu gry.

## Krok 4. Osoba od nazw i mapy

1. Odszukaj NazwaPokoju. Zachowaj jej nazwę, argument i typ wyniku.
2. Przed dostępem do tablicy rozpatrz numer zbyt mały i zbyt duży.
3. Dla poprawnego numeru sam oblicz indeks i zwróć element.
4. Uruchom dla wszystkich czterech numerów oraz dwóch błędnych — T2.9.
5. W Mapa zachowaj cztery wiersze i jeden znacznik pozycji. Dodaj drugi, odrębny opis odkrycia, oparty na bool z tego samego indeksu.
6. Nie zmieniaj w mapie `pokoj`, `energia` ani elementów tablic.

## Krok 5. Osoba od resetu i ruchu

1. W Start zaplanuj pętlę ustawiającą wszystkie odkrycia na false.
2. Po pętli oznacz tylko pozycję startową. Dlaczego odwrotna kolejność skasowałaby oznaczenie?
3. W Idz wskaż partnerowi ostatnią odmowę przed zatwierdzeniem pozycji.
4. Dopisz oznaczenie odwiedzin po zatwierdzeniu, nie przed kontrolą ściany i końca gry.
5. Nie dodawaj kolejnego wywołania ZakonczTure. Obecne nadal wystarczy.
6. Sprawdź w debuggerze lub chwilowym odczycie dwie flagi po prawo/lewo/prawo. Usuń tymczasowe komunikaty diagnostyczne przed commitem.

## Krok 6. Osoba od zliczania i nowej komendy

1. W projekcie prób uruchom poniższy **celowo nieukończony** przykład. Buduje się, ale jeszcze nie zlicza liczb.
2. Przed programowaniem wypisz ręcznie, które liczby spełniają warunek. Potem uzupełnij ciało pętli. Nie przenoś tego kodu wprost do gry — typ danych i reguła gry są inne.

## Krok 7. Połącz części

1. Każdy pokazuje diff drugiej osobie i wyjaśnia jeden przypadek odmowy albo granicy.
2. Integrator scala według kolejności z kontraktu; po każdej zmianie build.
3. Pozostali nie czekają: jedna osoba wykonuje próbę, druga porównuje wynik z kontraktem i przygotowuje przypadek graniczny. W parze te obowiązki rotują.
4. Wykonaj T2.1–T2.10 oraz stare TESTY.md. Zapisz rzeczywiste wyniki.
5. Przy błędzie wróć do najmniejszej funkcji, która go powoduje. Nie zmieniaj limitu energii, żeby „test przeszedł”.

## Krok 8. Odbiór i przekazanie

1. Każdy samodzielnie zmienia format odczytu bez zmiany danych i wyjaśnia rezultat.
2. Uporządkuj README i ZESPOL.md. Integrator oznacza rdzeń tagiem.
3. Dopiero teraz wybierz nice to have. Do C3 potrzebna jest wersja podstawowa, nie dodatek.
4. Na koniec zapisz trzy zdania dla przyszłego nowego członka: co działa, co nie działa, następny krok.

## Jeśli utkniesz

- Wyjątek indeksu: wypisz na kartce numer, indeks i Length — nie dodawaj przypadkowych +1/-1.
- Zły licznik: sprawdź tablicę przed funkcją i po niej; funkcja nie powinna nic zmienić.
- Konflikt Git: nie usuwaj cudzej sekcji. Wspólnie odtwórz uzgodniony kontrakt i uruchom próbę.
- Partner skończył: nie oddawaj mu całej swojej części. Poproś o pytanie naprowadzające lub pair programming z tobą przy klawiaturze.


# Kontrakt, współpraca i próby — pod ręką

## Kontrakt techniczny

| Element | Umowa |
|---|---|
| `string[] nazwyPokojow` | Dokładnie 4 niepuste nazwy wyświetlane. Kolejność odpowiada pokojom 1–4. Nie zmieniamy tablicy podczas rozgrywki. |

## Podział pracy bez czekania

- Najpierw wspólnie przeczytajcie kontrakt i wpiszcie właścicieli sekcji do ZESPOL.md. Integrator dodaje uzgodnione dwie tablice, zapisuje działającą bazę; pozostali w tym czasie wykonują mały eksperyment z tablicą w projekcie prób. Nie dodają drugich kopii tych samych zmiennych.
- Zespół 3-osobowy: A — tablica nazw, NazwaPokoju i Mapa; B — reset odkryć i oznaczanie przy udanym ruchu; C — PoliczOdwiedzone, PokazOdkrycia, pomoc i nowa gałąź rozdzielacza.
- Zespół 2-osobowy: A — nazwy, Mapa i reset; B — oznaczanie przy ruchu, licznik i odczyt. Pomoc/rozdzielacz dopisują wspólnie w parze, zmieniając kierowcę.
- A testuje mapę na tymczasowych lokalnych danych w projekcie prób; C testuje licznik na własnej bool[]; nie czekają na ruch B. B sprawdza flagi debuggerem lub tymczasowym odczytem usuwanym przed commitem.
- A i B nie edytują równocześnie inicjalizacji tablic. Po wspólnym przygotowaniu bazy pracują w uzgodnionych funkcjach.
- Po swojej części: każdy recenzuje cudzą gałąź i wykonuje próbę, której autor nie przeprowadził. Integracja: nazwy/mapa → reset/ruch → odczyt. Po każdej gałęzi build i próba.
- Jeśli funkcja jest zablokowana, para pracuje nad blokującą częścią przez 15 minut na zmianę; trzecia osoba przygotowuje niezależny test lub poprawia swój fragment. W ZESPOL.md zapiszcie przyczynę i następny krok.

## Git — obowiązkowy przebieg

- Przed pracą ustalcie nazwę głównej gałęzi w GitHubie i README. Przykład używa `master`, zgodnie z repozytorium bazowym; przy `main` zamieńcie nazwę we wszystkich poleceniach. Nie twórzcie przypadkowo drugiej głównej gałęzi.
- Pracujcie w katalogu z `.csproj`; jeśli gra działa, zakończcie ją przed poleceniami terminala.

```bash
git status
git switch master
git pull --ff-only
dotnet build
git switch -c feature/collab-zadanie
```

- `feature/collab-zadanie` zastąp własną nazwą, np. `feature/c02-nazwy` albo `feature/c03-dziennik`. Każda osoba używa innej gałęzi. Zacznij od czystego katalogu; własne zmiany zapisz przed przełączeniem.
- Po małej zmianie: `git diff`, `dotnet build`, `dotnet run`, właściwe próby, zamknięcie gry.
- Dodaj jawnie zmienione pliki przez `git add NAZWA_PLIKU` (to miejsce na prawdziwą nazwę), obejrzyj `git diff --staged`, zrób commit opisujący zmianę i `git push -u origin NAZWA_GALEZI`.
- Otwórz PR do faktycznej głównej gałęzi; kolega sprawdza warunki, reset i koszt. Integrator scala przez GitHub po jednej gałęzi; nie wykonuje drugiego merge tej samej zmiany lokalnie.
- Po każdym scaleniu pobierz główną gałąź do czystej kopii i wykonaj build oraz właściwe próby. Własną niezakończoną gałąź aktualizuj przez `git fetch origin`, potem `git merge origin/master` po zapisaniu swojej pracy w commicie.
- Jeśli wystąpi konflikt, przeczytaj obie wersje z autorem i sprawdź wynik. Bez force-push i resetowania w ciemno. `pull --ff-only` może odmówić przy rozbieżności — wtedy sprawdź historię.
- Końcowy tag tworzy tylko integrator na odebranej głównej gałęzi; nazwa tagu jest podana w briefie. Nie nadpisuj istniejącego tagu: użyj kolejnej wersji.
